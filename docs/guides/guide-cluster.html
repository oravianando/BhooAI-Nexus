GUIDE

Cluster Setup Link multiple hosts into a BhooAI Nexus cluster mesh — a node agent on every machine, a central registry on the master, a round-robin load balancer, and an RPS/CPU autoscaler. Per-node tokens, admin pairing, and cluster.runtime.json persistence.

The mesh at a glance

MASTER
registry central node book · cluster.runtime.json
lb round-robin reverse proxy · :8080
scale RPS/CPU + AI autoscaler

▼agent :7575▼
SLAVE · node-2

role backend
agent nexus node serve :7576
auth own per-node token
Every linked slave is round-robined by the master LB; all agent calls are Bearer-token gated. Each slave can run on its own machine — or several on one device, each with a unique --port.

1. Master config — nexus.config.ts

On the master, enable the cluster and declare the load balancer + node agent host/ports, and a pairing token. The master is the central registry that linked slaves register into:

cluster: {
  enabled: true,
  failOpenSingleNode: true,
  token: 'master-pairing-secret',      // used to link slaves
  lbHost: '0.0.0.0', lbPort: 8080,     // round-robin reverse proxy
  nodeAgentHost: '0.0.0.0',             // bind all interfaces (remote access)
  nodeAgentPort: 7575,
  registryFile: 'cluster.runtime.json',   // gitignored — master stores linked nodes here
  autoscale: {
    enabled: true, mode: 'auto',
    minNodes: 1, maxNodes: 4,
    cooldownMs: 60_000,
    cpuHigh: 80, rpsPerNodeHigh: 15, rpsPerNodeLow: 5,
  },
}
nodeAgentHost: '0.0.0.0' Bind 0.0.0.0 so the agent is reachable from remote machines. localhost or 127.0.0.1 blocks off-host linking — a common gotcha when slaves are on another box.

2. Slave setup — nexus node serve

On each slave, start the node agent with a role and port. The agent announces its services to the master and heartbeats on a schedule:

# on the slave machine, from its project root
nexus node serve --role=backend --port=7575

The slave's own nexus.config.ts must set the same cluster.token the master will send (or a per-node token — see below). Verify the agent is alive before linking:

curl http://<slave-host>:7575/info \
  -H "Authorization: Bearer <slave-token>"
# {"id":"...-backend","role":"backend","baseUrl":"http://localhost:7575",...}

2b. Multiple nodes on a single device

You don't need separate machines to experiment with the mesh. A single computer can run the master and several slave agents at once. The only rule: each agent needs its own port and its own project directory. Use a distinct --port per agent, and point each nexus node serve at a different project root so their service ports (4000, 4001, …) and node ids don't collide.

Option A — separate project folders (recommended)

Scaffold one project per node with nexus init, give each a unique backend port, then start each agent from its own folder:

# terminal 1 — master (project "app-master")
nexus init app-master --as=root --skip-mongo-check
cd app-master && nexus cluster serve

# terminal 2 — slave node-2 (project "app-node2")
nexus init app-node2 --as=node --name app-node2 --skip-mongo-check
cd app-node2 && nexus node serve --role=backend --port=7575

# terminal 3 — slave node-3 (project "app-node3", different port)
nexus init app-node3 --as=node --name app-node3 --skip-mongo-check
cd app-node3 && nexus node serve --role=backend --port=7576

Because they're separate projects, the wizard auto-detects the master's pairing token from the sibling app-master folder and reuses it. Link them from the master:

# from app-master
nexus cluster link http://localhost:7575
nexus cluster link http://localhost:7576

Option B — one project, multiple agents with a port override

You can also run several agents from the same project by overriding the port on the command line. This works but the agents share the same node id (same project root), so use it only for a quick sanity check — the registry keys nodes by id, and duplicates overwrite each other.

# same project root, different agent ports (id collision risk — test only)
nexus node serve --role=backend --port=7575
nexus node serve --role=backend --port=7576   # second window
ports must be unique per process cluster.nodeAgentPort is the default agent port. Use --port to override it per agent so two agents on one machine never fight for the same port. The LB on the master stays at cluster.lbPort (8080) and needs no change.

3. Per-node tokens

Each slave has its own token. When you link it, the master stores that token as authToken in the node's registry record and uses it for every subsequent agent call (/info, /health, /exec, /metrics):

// in cluster.runtime.json (master side, gitignored)
{
  "nodes": [{
    "identity": { "id": "a453d9a9e220-backend", "role": "backend", ... },
    "status": "ready",
    "enabled": true,
    "authToken": "a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6"   // slave's token, stored on master
  }]
}

Slave mode — Generate token button

The admin console's Slave mode has a Generate token button that creates a fresh random token and writes it into both nexus.runtime.json and .env on the slave. Restart the node agent so it picks up the new token, then paste it into the master's link dialog.

Slave mode also shows the full pairing token, node id, role, agent port, and agent URL, plus Start node / Stop node buttons that launch nexus node serve --role=backend --port=<nodeAgentPort> for you. The same controls (start/stop the LB + autoscaler) live beside the mode toggle in Master mode.

Pairing success — congratulations overlay

When a node links successfully, the master admin shows a full-screen CONGRATULATIONS overlay with flying ribbons. It stays until dismissed and lists the linked node's details fetched from the slave: project (from the slave's package.json name), node id, role, version, agent URL, and each service URL.

4. Admin panel — Master Mode → Link node

The pairing flow is driven from the master's admin console:

  1. Open Admin → Cluster → Master Mode.
  2. Paste the slave's agent URL (e.g. http://192.168.1.8:7575).
  3. Click Link node — a pairing dialog opens asking for the slave's token.
  4. Paste the token the slave generated (or its cluster.token).
  5. The master calls POST /admin/cluster/link, which hits the slave's /info and /health with the token; on success the node is added to cluster.runtime.json.

Link API

POST /admin/cluster/link
Authorization: Bearer <master-admin-jwt>
x-csrf-token: <fresh csrf token>
Content-Type: application/json

{ "nodeUrl": "http://192.168.1.8:7575", "token": "a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6" }

# 200 OK
{ "node": { "identity": { ... }, "status": "pending", "authToken": "a1b2..." } }
CSRF rotates /admin/cluster/link is a POST under CSRF + admin auth. The CSRF token rotates on every safe request — re-fetch GET /csrf-token immediately before the link POST. See the Postman testing guide for a worked 3-step flow.

5. Load balancer — round-robin on lbPort

The LB is a plain node:http reverse proxy on cluster.lbPort (default 8080). It round-robins across every ready backend node, streams raw bodies through untouched (so SSE and uploads still work), and stamps x-bhooai-node on every response. Start and stop it from the admin panel or the CLI:

nexus cluster start     # start the LB
nexus cluster stop      # stop the LB (slaves keep running)
nexus cluster status    # linked nodes + per-node RPS

6. Autoscaler — RPS / CPU thresholds

Every 10s the Autoscaler samples the LB's RPS histogram and each node's /metrics. It scales within minNodes/maxNodes with a cooldown so it doesn't thrash:

ConditionAction
per-node RPS > rpsPerNodeHigh (15)scale up (+1 node, up to maxNodes)
CPU > cpuHigh (80%)scale up
per-node RPS < rpsPerNodeLow (5)scale down (−1 node, down to minNodes)
within cooldownMs of last actionhold (skip)
AI advisor says scale-up|scale-down|hold off-railfall back to the deterministic rules

7. cluster.runtime.json — gitignored

The master persists linked nodes to cluster.runtime.json at the repo root. It is gitignored — it is runtime state, not source. Surviving a master restart means the file is intact; deleting it clears the registry:

# .gitignore
cluster.runtime.json
nexus.runtime.json

8. Node agent API — Bearer token auth

Every agent route requires Authorization: Bearer <token> matching the slave's cluster.token (or its generated per-node token):

RouteMethodReturns
/infoGETNodeIdentity — id, role, tier, baseUrl, services, capabilities
/healthGETNodeHealth — probes the role service's /health
/metricsGETNodeMetricsSample — rps, cpu, memoryMb, sampledAt
/execPOSTNodeExecResult — allowlist: start / stop / restart / logs / update
 
curl http://<slave>:7575/metrics \
  -H "Authorization: Bearer a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6"
# {"rps":12.4,"cpu":41,"memoryMb":318,"sampledAt":"2026-08-10T03:15:00Z"}

9. Troubleshooting

[cluster] scale-up requested but no standby backend node

informational — not an error The autoscaler (deterministic rule or AI advisor) decided the cluster should grow, but there is no standby backend node to enable. The autoscaler can only flip a pre-linked, disabled (enabled: false) node to enabled: true — it cannot provision brand-new machines. When you link a node it defaults to enabled: true, so a single linked node leaves nothing to scale into. The message is rate-limited to once a minute and is harmless in single-node setups. 
# how to actually enable autoscaling
# 1. Link 2+ backend slaves (nexus node serve --role=backend --port=7575)
nexus cluster link http://<slave-2>:7575
# 2. Mark the extra node(s) as standby via the admin Cluster table (enabled=false),
#    or set autoscale.mode: 'manual' in nexus.config.ts to silence the advisor.

cluster.enabled is false — set cluster: { enabled: true, ... }

stale runtime override Your nexus.config.ts may correctly say enabled: true, but nexus.runtime.json (written by the admin Stop button) overrides it because runtime config beats the user config in the loader precedence. Running nexus cluster serve now re-enables the cluster in runtime automatically, but for older installs clear it manually: 
# nexus.runtime.json
{ "cluster": { "enabled": true } }   // was { "cluster": { "enabled": false } }

POST /admin/cluster/generate-token: 404 or POST /admin/cluster/node/start: 404

stale backend routes The node-agent lifecycle routes (/admin/cluster/node/status, /admin/cluster/node/start, /admin/cluster/node/stop) and /admin/cluster/generate-token were added after some projects were scaffolded. If your backend was copied from an older template, the routes are missing and the admin returns 404. Restart the backend after pulling the framework update, or re-scaffold the affected app from packages/nexus-cli/templates/apps/backend/src/modules/admin/clusterRoutes.ts.

400 {"error":"fetch failed"}

agent not running The master cannot reach the slave's agent. Verify the agent process is up and the port is listening: 
# Windows
Get-NetTCPConnection -State Listen | Where-Object LocalPort -eq 7575
# start it if missing
nexus node serve --role=backend --port=7575
Also check the URL — use http://192.168.1.8:7575, not localhost, when the slave is on another machine.

400 {"error":"agent 401 /info"}

wrong token The token in the link body doesn't match the slave's cluster.token. Check both the slave's nexus.config.ts and its nexus.runtime.json (the runtime file overrides). If you used Generate token in the admin UI, restart the node agent so it picks up the new token before linking.

401 Unauthorized (empty body)

CSRF mismatch The x-csrf-token header doesn't match the nexus_csrf cookie. The cookie rotates on every safe request, so re-run GET /csrf-token immediately before the link POST. In Postman, re-run Step 1 right before Step 3 — see the Postman testing guide for the exact sequence.

403 Forbidden

not an admin The logged-in user lacks the admin role. Verify in MongoDB: db.users.findOne({email:"..."}, {roles:1}). Only roles: ["admin"] can call /admin/cluster/*.
Fail-open When cluster.enabled is off (default) or the mesh is down, the app keeps working on a single node — a deliberate availability choice. The cluster is an optimization, not a dependency.
