GUIDE

Upload Files Multipart form-data uploads through the Node backend — CSRF-protected POST, UUID-renamed files served from a static /uploads/* route, with size/count/type validation.

The flow

Browser ──> GET /csrf-token ──> POST /uploads (multipart, x-csrf-token) ──> uploads/<uuid>.ext
                                                                        400 on too-large / too-many / wrong-type
GET /uploads/<uuid>.ext ──> serveStatic middleware ──> file bytes

1. Register the upload routes

In apps/backend/src/main.ts the registerUploadRoutes() call wires both the multipart POST handler and the static file middleware that serves the stored files back:

import { registerUploadRoutes } from './modules/uploads/uploadsRoutes.js';

registerUploadRoutes(app, {
  uploadDir:   path.resolve('uploads'),
  urlPrefix:   '/uploads',
  maxFileSize: config.uploads.maxFileSize,
  maxFiles:    config.uploads.maxFiles,
  allowedTypes:config.uploads.allowedTypes,
});

// static middleware for GET /uploads/*
app.use('/uploads', serveStatic(uploadDir, { immutable: true, maxAge: 31536000 }));

2. Configuration — nexus.config.ts

uploads: {
  maxFileSize:  5 * 1024 * 1024,   // 5 MB per file
  maxFiles:     10,               // per single POST
  allowedTypes: [
    'image/png', 'image/jpeg', 'image/webp', 'image/gif',
    'application/pdf',
    'text/plain',
  ],
}
Per-file limit maxFileSize applies to each file, not the whole body. A 10-file POST where every file is 4 MB is allowed; a single 6 MB file is rejected with 400.

3. CSRF flow — GET /csrf-token first

Because the upload is a POST, it needs a CSRF token. The double-submit pattern requires the x-csrf-token header to match the nexus_csrf cookie. Fetch a token on page load (a GET, which also sets the cookie):

const r = await fetch('/csrf-token', { credentials: 'same-origin' });
const { token } = await r.json();
// store `token` and send it in the x-csrf-token header on the POST

4. Full example — profile picture upload form

<!-- HTML -->
<form id="pic-form" enctype="multipart/form-data">
  <input type="file" name="avatar" accept="image/*" required />
  <button type="submit">Upload</button>
</form>
<img id="preview" hidden />
// JS — fetch the CSRF token, then POST FormData
let csrfToken;
(async () => {
  const r = await fetch('/csrf-token', { credentials: 'same-origin' });
  csrfToken = (await r.json()).token;
})();

document.getElementById('pic-form').addEventListener('submit', async (e) => {
  e.preventDefault();
  const form = e.currentTarget;
  const fd = new FormData(form);          // multipart/form-data, browser sets the boundary

  const res = await fetch('/uploads', {
    method: 'POST',
    credentials: 'same-origin',
    headers: { 'x-csrf-token': csrfToken },  // do NOT set Content-Type; fetch does it
    body: fd,
  });

  if (!res.ok) {
    const err = await res.json().catch(() => ({}));
    alert('Upload failed: ' + (err.error || res.status));
    return;
  }

  const { files } = await res.json();
  const img = document.getElementById('preview');
  img.src = files[0].url;                 // /uploads/<uuid>.png
  img.hidden = false;
});
Don't set Content-Type When sending FormData with fetch, do not set Content-Type: multipart/form-data yourself. The browser must set the boundary automatically; a manually-set header omits the boundary and the parser fails.

5. Success response

Files are stored in the uploads/ directory with a random UUID filename. The original name is discarded; only the extension is preserved. The response returns the public URL for each file:

{
  "files": [
    {
      "field": "avatar",
      "originalName": "me.png",
      "storedName": "9f1c2d8a-3b7e-4a01-9c12-6d8e5f4a7b21.png",
      "url": "/uploads/9f1c2d8a-3b7e-4a01-9c12-6d8e5f4a7b21.png",
      "size": 482113,
      "type": "image/png"
    }
  ]
}

6. Validation errors (400)

The handler validates before writing to disk. Any failure returns 400 with a JSON error body and no file is stored:

ConditionResponse bodyStatus
One file exceeds maxFileSize{"error":"file too large","limit":5242880,"size":...}400
More files than maxFiles{"error":"too many files","limit":10,"count":12}400
MIME type not in allowedTypes{"error":"file type not allowed","type":"application/x-msdownload"}400
Missing CSRF tokenempty body401
No files in the POST{"error":"no files received"}400
MIME sniffing The handler trusts the Content-Type the browser sends for the allowedTypes check, but also reads the magic bytes for image types. A file claiming image/png that isn't a real PNG is rejected. Treat uploads as untrusted — serve them from a static route with Content-Disposition: inline and never eval uploaded content.

7. Where files live

ConcernDetail
Directoryuploads/ at the backend root (configurable via uploads.uploadDir)
FilenamesRandom UUID v4 + original extension, e.g. <uuid>.png
Public URL/uploads/<uuid>.ext served by the static middleware
gitignoreuploads/ is gitignored — it is runtime data, not source
BackupsBack it up separately from the repo; it is not in version control
Bring your own storage For production swap the local write for S3 / GCS / Azure Blob: keep the same {files:[{url}]} response shape and the browser code doesn't change at all.
