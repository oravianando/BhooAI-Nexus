GUIDE

WebSocket Chat Realtime rooms, broadcasts, and WebRTC signaling over the Nexus WebSocket server — with a full browser chat example and the complete message-type reference.

The Nexus realtime server (@bhooai/nexus-realtime) attaches to the same HTTP server as the REST API. It authenticates on upgrade, tracks rooms per instance, and can fan out across machines via a Redis pub/sub adapter. This guide shows the full browser chat flow.

1. How the server is wired

The scaffold already wires RealtimeServer in apps/backend/src/main.ts. It listens on config.ws.path (default /ws) on the backend port (default 4000).

// apps/backend/src/main.ts (already generated)
const realtime = new RealtimeServer({
  httpServer: server.httpServer,
  path: config.ws.path,                 // '/ws'
  authService,                         // verify ?token= on upgrade
  csrfOptions: config.ws.requireCsrf ? { trustedOrigins: trustedOrigins(config) } : undefined,
});

The server attaches to the HTTP server's upgrade event and only handles its own path. The upgrade is the security boundary — WebSockets have no CORS preflight, so CSRF + origin are checked here.

2. Browser connection

const ws = new WebSocket('ws://localhost:4000/ws?token=' + accessToken);
Auth on upgrade The access token is passed via the ?token= query parameter or the Sec-WebSocket-Protocol subprotocol header. Without a valid token the server writes HTTP/1.1 401 Unauthorized and destroys the socket. If requireAuth is false (or no authService is passed), anonymous connections are allowed and get a random id.

3. Message format

Every message is a JSON object. The type field dispatches it. Not every field is present on every type — the table below shows which.

{
  type: 'join' | 'leave' | 'broadcast' | 'offer' | 'answer' | 'candidate' | 'media' | 'ping',
  room: string,         // join/leave/broadcast
  event: string,        // broadcast
  data: unknown,        // broadcast
  to: string,           // offer/answer/candidate — peer connection id
  from: string,         // server-side only — the sender's id
  sdp: string,          // offer/answer
  candidate: unknown,   // candidate
  action: string,        // media — mediasoup signaling action
  payload: Record,      // media
}

4. Join a room

ws.send(JSON.stringify({ type: 'join', room: 'general' }));

// Server responds with the current local peers (excluding you)
{ type: 'joined', room: 'general', peers: ['conn:abc', 'conn:def'] }

// Everyone else in the room is told you joined
{ type: 'peer-joined', room: 'general', peer: 'conn:you' }

5. Leave a room

ws.send(JSON.stringify({ type: 'leave', room: 'general' }));

// You get an ack
{ type: 'left', room: 'general' }

// Everyone else is told you left
{ type: 'peer-left', room: 'general', peer: 'conn:you' }

6. Broadcast to a room

ws.send(JSON.stringify({
  type: 'broadcast',
  room: 'general',
  event: 'message',
  data: { text: 'hello everyone' },
}));

// Every other member of 'general' receives:
{
  type: 'broadcast',
  room: 'general',
  from: 'conn:you',
  event: 'message',
  data: { text: 'hello everyone' }
}
No echo to self deliverRoom skips the originator, so you never receive your own peer-joined, peer-left, or broadcast echo. This is intentional — it avoids the "I see my own message" bug.

7. Full chat example — client-side JavaScript

// chat.js — drop into a page with a <ul id="log"></ul> and <input id="msg">
let ws;
let myId;

function connect(accessToken, room) {
  ws = new WebSocket('ws://localhost:4000/ws?token=' + accessToken);

  ws.onopen = () => {
    log('⚡ connected');
    send({ type: 'join', room });
  };

  ws.onmessage = (e) => {
    const msg = JSON.parse(e.data);
    switch (msg.type) {
      case 'joined':
        myId = msg.peers.length ? 'conn:me' : 'conn:me'; // id assigned by server
        log('✓ joined ' + msg.room + ' with peers: ' + msg.peers.join(', '));
        break;
      case 'peer-joined':
        log('→ ' + msg.peer + ' joined');
        break;
      case 'peer-left':
        log('← ' + msg.peer + ' left');
        break;
      case 'broadcast':
        if (msg.event === 'message') {
          log(msg.from + ': ' + (msg.data && msg.data.text));
        }
        break;
      case 'left':
        log('✗ left ' + msg.room);
        break;
      case 'error':
        log('✗ error: ' + msg.message);
        break;
    }
  };

  ws.onclose = () => log('⚡ disconnected');
}

function send(obj) { ws.send(JSON.stringify(obj)); }

function sendChat(text, room) {
  send({ type: 'broadcast', room, event: 'message', data: { text } });
}

function leave(room) { send({ type: 'leave', room }); }

function log(line) {
  const li = document.createElement('li');
  li.textContent = new Date().toLocaleTimeString() + ' ' + line;
  document.getElementById('log').appendChild(li);
}

// Wire it up
connect(accessToken, 'general');
document.getElementById('msg').addEventListener('keydown', (e) => {
  if (e.key === 'Enter' && e.target.value.trim()) {
    sendChat(e.target.value.trim(), 'general');
    e.target.value = '';
  }
});

8. WebRTC signaling

For 1:1 video/voice, peers exchange offers, answers, and ICE candidates through the room. The server relays them peer-to-peer (same instance) or via the conn:<to> pub/sub channel (cross-instance).

// Peer A — create offer
const pc = new RTCPeerConnection({ iceServers: [{ urls: 'stun:stun.l.google.com:19302' }] });
pc.onicecandidate = (e) => {
  if (e.candidate) {
    send({ type: 'candidate', to: peerBId, candidate: e.candidate.toJSON() });
  }
};
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
send({ type: 'offer', to: peerBId, sdp: offer.sdp });

// Peer B — answer
ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  if (msg.type === 'offer') {
    pc.setRemoteDescription({ type: 'offer', sdp: msg.sdp });
    const answer = await pc.createAnswer();
    await pc.setLocalDescription(answer);
    send({ type: 'answer', to: msg.from, sdp: answer.sdp });
  } else if (msg.type === 'candidate') {
    pc.addIceCandidate(msg.candidate);
  }
};

For multi-party routing, the optional mediasoup SFU adapter relays media via type: 'media' messages — see the Realtime API reference for the full action list.

9. Heartbeat (ping/pong)

// Client
setInterval(() => ws.readyState === WebSocket.OPEN &&
  ws.send(JSON.stringify({ type: 'ping' })), 30_000);

// Server responds
{ type: 'pong' }

The server config also has ws.heartbeatMs (default 30s) for connection liveness tracking.

Scaling across machines Members per room are tracked per instance. Direct peer messages publish to conn:<id>; room events publish to room:<room>. With the RedisPubSubAdapter, any instance delivers to its local members — that's how chat scales across machines without changing the client code.
