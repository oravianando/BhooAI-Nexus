@bhooai/nexus-graphql GraphQL API graphql-js + a custom federation/gateway layer (no Apollo).

A self-contained GraphQL stack: defineSubgraph builds federation-compliant subgraphs, createGateway executes a single subgraph in-process, createFederatedGateway composes multiple subgraphs and executes federated queries (root pass + iterative entity-join passes). Subscriptions run over WebSocket via the graphql-transport-ws protocol. No Apollo dependency — composition and execution are ours; the directive surface matches Federation v2 so subgraph SDL stays interoperable.

An entity representation: __typename plus the key fields of an entity. This is what _entities(representations: [_Any!]!) receives and what the federated executor builds from a parent object's @key fields to join across subgraphs.

EntityResolver

Resolves an entity by its representation. Returns the object (with fields) or null. Subgraph

defineSubgraph(options)

function defineSubgraph(options: DefineSubgraphOptions): Subgraph

Define a federation-compliant subgraph from user typeDefs + resolvers. The user SDL may use federation directives (@key, @external, @requires, @provides, @extends). defineSubgraph:

  1. Parses @key directives via parseEntityKeys to learn entity types + key field paths.
  2. Builds the _Entity union SDL via entityUnionSdl and wires its resolveType to read __typename off the resolved value.
  3. Prepends the federation directive definitions (FEDERATION_DIRECTIVE_SDL), the @link clause (FEDERATION_LINK), and appends the federation boilerplate types (FEDERATION_TYPES + the _Entity union) so buildSchema accepts the schema.
  4. Auto-wires Query._service (returns { sdl }), Query._entities (calls entityResolver per representation), the _Any scalar (pass-through), and _Service.sdl.
  5. Validates the SDL parses standalone and returns the Subgraph object.

defineSubgraph does not compose — it produces a single executable subgraph. createGateway executes it in-process for the single-subgraph case; createFederatedGateway composes multiple subgraphs.

const users = defineSubgraph({
  name: 'accounts',
  typeDefs: `
    type User @key(fields: "id") { id: ID! email: String! roles: [String!]! }
    type Query { me: User users(limit: Int): [User!]! }
  `,
  resolvers: {
    Query: {
      me: (_p, _a, ctx) => ctx.user,
      users: (_p, { limit }, ctx) => ctx.db.User.find().limit(limit).lean(),
    },
  },
  entityResolver: (rep, ctx) => ctx.db.User.findById(rep.id).lean(),
});

const gateway = createGateway({ subgraph: users });
router.post('/graphql', graphqlHttpHandler({
  gateway,
  introspection: true,
  context: async (ctx) => ({ request: ctx, user: ctx.state.user, db }),
}));
Entity resolution There is no __resolveReference field. Entity resolution is via the entityResolver option of DefineSubgraphOptions, which the auto-wired _entities field calls once per representation.
name is required DefineSubgraphOptions.name is required — it is the subgraph identity used in composition (Supergraph.ownership, Supergraph.entities).

validateOperation(schema, source)

function validateOperation(schema: GraphQLSchema, source: string): string[]

Validate a query string against a schema before execution. Parses the source (returns the parse error message in the array on failure), then runs graphql-js validate and returns an array of error messages (empty = valid). Useful for the HTTP handler to reject malformed operations early.

const errs = validateOperation(gateway.schema, query);
if (errs.length) return res.json({ errors: errs.map((m) => ({ message: m })) });

parseEntityKeys(typeDefs)

function parseEntityKeys(typeDefs: string): Map<string, string[]>

Parse @key(fields: "...") directives from subgraph SDL to learn which types are entities and what their key field paths are. A pragmatic regex scan (not a full SDL parser) — sufficient for the v1 federation subset. Composite keys like @key(fields: "id tenant") are supported (space-separated, as in the spec).

Returns a Map<typeName, string[]> of key field names (flattened — a composite key yields ["id","tenant"]). Types with no @key are absent. Used by defineSubgraph; also usable directly to inspect SDL.

const keys = parseEntityKeys(`type User @key(fields: "id tenant") { id: ID! tenant: String! }`);
// Map { "User" => ["id","tenant"] }

Federation directives

FEDERATION_DIRECTIVE_SDL

const FEDERATION_DIRECTIVE_SDL: string

The federation directive definitions, prepended to the user's typeDefs so buildSchema accepts the federation directives. We target a Federation v2-style subset (the same directives Apollo uses); composition is ours, but the directive surface matches the spec so subgraph SDL is interoperable.

directive @link(url: String!, import: [String!]) on SCHEMA
directive @key(fields: String!) repeatable on OBJECT | INTERFACE
directive @external on FIELD_DEFINITION
directive @requires(fields: String!) on FIELD_DEFINITION
directive @provides(fields: String!) on FIELD_DEFINITION
directive @extends on OBJECT | INTERFACE | FIELD_DEFINITION

const FEDERATION_LINK: string

The extend schema @link(...) clause advertising the federation import. Prepended to the published subgraph SDL (what _service.sdl returns).

Federation boilerplate types appended to make a schema subgraph-compliant: the _Any scalar, the _Service type, and the Query._service / Query._entities root fields. The _Entity union is generated separately by entityUnionSdl (it depends on the entity type names).

entityUnionSdl(entityTypeNames)

function entityUnionSdl(entityTypeNames: string[]): string

Build the _Entity union SDL for the given entity type names. Returns scalar _Entity when there are no entities (so the schema still parses), otherwise union _Entity = A | B | C. Used by defineSubgraph.

FEDERATION_DIRECTIVE_NAMES

const FEDERATION_DIRECTIVE_NAMES: string[]

Names of the federation directives we recognize: ['key','external','requires','provides','extends','link']. Used for stripping when building the public schema (see buildPublicSchema).

Gateway

createGateway(input)

function createGateway(
  input: { subgraph: Subgraph } | { subgraphs: Subgraph[] },
): Gateway

Create an in-process gateway over one or more subgraphs. The input is a union:

  • { subgraph: Subgraph } — single-subgraph mode (the default app shape).
  • { subgraphs: Subgraph[] } — multi-subgraph. Currently throws a clear "not yet" error for >1 subgraph — use createFederatedGateway for multi-subgraph federation. A single-element subgraphs array is accepted.

In single-subgraph mode the gateway exposes the subgraph's public schema (federation internals stripped via buildPublicSchema) and executes operations directly against the subgraph's resolvers — no network hop, shared in-process context (DB pool, services). Federation overhead only kicks in with createFederatedGateway.

// single subgraph (either form works)
const gw1 = createGateway({ subgraph: users });
const gw2 = createGateway({ subgraphs: [users] });

// execute in-process
const result = await gw1.execute({
  document: parse('query { me { id email } }'),
  contextValue: { user, db },
});
Multi-subgraph Passing >1 subgraph to createGateway throws — it is forward-compatible but not implemented here. Use createFederatedGateway for composition + federated execution.

createFieldResolver(resolvers)

function createFieldResolver(resolvers: Resolvers): GraphQLFieldResolver<any, GraphQLContext>

Build a graphql-js fieldResolver that dispatches to the user's resolvers map. Used internally by createGateway and executeFederated. Resolution order:

  1. __typename → the parent's __typename (or the field's parent type name).
  2. resolvers[typeName][fieldName] — if it's a { resolve, subscribe } shape (subscription field), use .resolve; otherwise call it directly.
  3. Default property access: parent[fieldName] (works for DB docs/objects).

createSubscribeFieldResolver(resolvers)

function createSubscribeFieldResolver(resolvers: Resolvers): GraphQLFieldResolver<any, GraphQLContext>

Build a subscribeFieldResolver for subscription root fields. Looks up resolvers[typeName][fieldName].subscribe and throws if absent (No 'subscribe' resolver for <Type>.<field>). Used internally by createGateway for the subscribe() path.

buildPublicSchema(subgraphSdl)

function buildPublicSchema(subgraphSdl: string): GraphQLSchema

Strip federation directives from subgraph SDL to produce the public (client-facing) schema. The gateway exposes this clean schema; the federation internals (_service, _entities, @key, @external, @link, …) are not part of the public API. For the single-subgraph case the public schema is simply the user's types without the federation markers. Stripping is regex-based: drops the extend schema @link(...) clause, standalone @link(...), and the @key/@requires/ @provides/@external/@extends directives, then collapses leftover blank lines and builds the schema.

graphqlHttpHandler(options)

function graphqlHttpHandler(options: GraphqlHandlerOptions): Handler

HTTP handler for /graphql. Returns a Handler (from @bhooai/nexus-core) suitable for router.post('/graphql', graphqlHttpHandler(...)). Accepts POST with { query, variables, operationName } (or GET with ?query=). Applies the gateway in-process. Introspection is rejected with 403 when introspection: false; a missing query returns 400; a parse error returns 400 with the graphql-js message.

router.post('/graphql', graphqlHttpHandler({
  gateway,
  introspection: config.graphql.introspection,
  context: async (ctx) => ({ request: ctx, user: ctx.state.user, db, pubsub }),
}));

Internally: parses the query, checks introspection, builds contextValue via options.context(ctx) (or the default), calls gateway.execute({ document, variableValues, operationName, contextValue }), and responds with JSON.

Subscriptions

PubSub

class PubSub {
  constructor();
  publish(topic: string, payload: unknown): void;
  asyncIterator(topics: string | string[]): AsyncIterable<any>;
}

Minimal in-process PubSub for GraphQL subscriptions, built on node:events. Sufficient for the single-instance default app; a Redis-backed pub/sub adapter can be plugged in later for cross-instance fanout. The EventEmitter max listeners is set to 0 (unlimited).

MethodDescription
publish(topic, payload)Emit payload to topic (synchronous EventEmitter.emit).
asyncIterator(topics)Return an AsyncIterable that yields payloads published to the topic(s). Accepts a single topic or an array. The iterator's return() removes all listeners (call on early completion / client disconnect).
 
const pubsub = new PubSub();

// in a resolver:
Subscription: {
  userCount: {
    subscribe: () => pubsub.asyncIterator('USER_COUNT'),
    resolve: () => User.countDocuments(),
  },
}

// publish from anywhere:
pubsub.publish('USER_COUNT', 1);
Backpressure The async iterator buffers payloads in an internal queue when the consumer is slow (no backpressure pressure on the emitter). Fine for the default single-instance app; use a bounded adapter for high-throughput fanout.

SubscriptionServer

class SubscriptionServer {
  constructor(opts: SubscriptionServerOptions);
  close(): Promise<void>;
}

GraphQL subscriptions over WebSocket (the graphql-transport-ws protocol). Attaches to an HTTP server's upgrade event. On connection_init we (optionally) authenticate; on subscribe we run the gateway's subscribe() and stream each next result back until the client sends complete or the socket closes. Handles ping/pong keepalive. Requires the graphql-transport-ws subprotocol (rejects the upgrade with 400 otherwise).

const subs = new SubscriptionServer({
  httpServer: server.httpServer,
  gateway,
  path: '/graphql/ws',
  authService,
  context: (_init, user) => ({ user, pubsub }),
});

// ...later, shutdown:
await subs.close();

Per-subscription flow: parse the query → validate against gateway.schema → build contextValue via options.context(init, user) → call gateway.subscribe({ document, variableValues, operationName, contextValue }) → pump next messages until the stream ends or the client sends complete. On socket close/error, all active iterators are returned (cleaned up).

contextValue, not context Both Gateway.execute and Gateway.subscribe take contextValue in their params (see ExecuteParams). The context-builder callbacks are on the handler options: GraphqlHandlerOptions.context (HTTP) and SubscriptionServerOptions.context (WS). They produce the contextValue that is forwarded to the gateway.

Federation

Single-subgraph is the default (in-process execute() against the public schema with federation directives stripped). Multi-subgraph opts into createFederatedGateway, which composes the subgraphs and executes federated queries. The flow is:

const gateway = createFederatedGateway([users, orders]);
// → composeSupergraph (ownership + @key entity sources + @provides/@requires records → supergraph SDL)
//   → executeFederated (root pass: group top-level fields by owner + execute trimmed subqueries;
//      iterative entity-join passes: one _entities call per missing-fields job, max 8 passes)

// inspect the fetch plan for a query (golden tests / debugging):
const plan = gateway.plan(parse('query { me { id orders { id total } } }'));

composeSupergraph(subgraphs)

function composeSupergraph(subgraphs: Subgraph[]): Supergraph

Compose multiple subgraphs into a Supergraph: collect field ownership, entity @key sources, @provides and @requires records, and a merged public SDL. Throws if subgraphs is empty.

Ownership rule (v1): a field is owned by a subgraph if that subgraph's SDL defines the field on the type and it is NOT @external. The first subgraph to claim a non-external field wins; a conflicting claim by a second subgraph is recorded as a composition warning (real federation would arbitrate via @shareable/@override — out of scope for v1). The merged SDL is built from the owning subgraph's public schema field types.

executeFederated(supergraph, document, variableValues, contextValue)

async function executeFederated(
  supergraph: Supergraph,
  document: DocumentNode,
  variableValues: Record<string, any> | undefined,
  contextValue: GraphQLContext,
): Promise<ExecutionResult>

Execute a federated query in-process against the composed subgraphs. Algorithm:

  1. Root pass — group the operation's top-level fields by their owning subgraph; for each group, execute a trimmed subquery against that subgraph in-process. Trim keeps only fields owned by that subgraph, plus __typename and entity key fields (so later passes can join). Fragment spreads at root are ignored in v1.
  2. Iterative entity-join passes — scan the stitched result for entity-typed objects whose requested fields are owned by other subgraphs; for each missing-fields job, build a representation from the parent's key fields, call that subgraph's _entities with a single representation and a trimmed subquery, then merge the returned fields back by index. Repeat until no missing fields remain (handles nested joins, one level per pass). Capped at 8 passes.

Each subgraph is executed in-process via graphql-js execute against the subgraph's federation schema + its resolvers (with createFieldResolver). Entity fetches are sequential — one _entities call per job with one representation, not batched across multiple parent objects of the same type.

@requires @requires is supported as "fetch the required external fields first, then resolve". @provides is recorded during composition (Supergraph.provides) but is not used to short-circuit field fetches in executeFederated — the executor always goes through the entity-join flow. @shareable arbitration and @override are not implemented in v1.
Sequential, in-process v1 execution is sequential (no parallel fetch fan-out) and in-process (shared nothing / distributed subgraphs over HTTP is designed, not built). Subscriptions are not federated in v1 — route them to the owning subgraph's SubscriptionServer.

createFederatedGateway(subgraphs)

function createFederatedGateway(subgraphs: Subgraph[]): FederatedGateway

Compose multiple subgraphs into a federated gateway. Takes a bare array of subgraphs (not { subgraphs: [...] }). The gateway exposes the merged public schema and executes queries via the sequential federated executor (root fetches + iterative entity-join passes). Subscriptions are not federated in v1 — route them to the owning subgraph's SubscriptionServer.

const accounts = defineSubgraph({ name: 'accounts', typeDefs, resolvers, entityResolver });
const orders = defineSubgraph({ name: 'orders', typeDefs2, resolvers2, entityResolver2 });

const gateway = createFederatedGateway([accounts, orders]);

router.post('/graphql', graphqlHttpHandler({
  gateway,
  context: async (ctx) => ({ request: ctx, user: ctx.state.user, db }),
}));

// inspect the fetch plan:
const plan = gateway.plan(parse('query { me { id orders { total } } }'));
Signature createFederatedGateway(subgraphs: Subgraph[]) — a bare array, not { subgraphs: [...] }. This differs from createGateway, which takes the union { subgraph } | { subgraphs }.

Federation subset (v1)

supported @key (single + composite, repeatable), @external, @requires (fetch required external fields first, then resolve), @provides (recorded in composition; not used to short-circuit execution), @extends, _entities, _service { sdl }, @link (declared, import list not enforced).

deferred @shareable arbitration (first-owner-wins instead), @override, @inaccessible enforcement, subscription federation (route to the owning subgraph's SubscriptionServer for now), parallel fetch fan-out, distributed (over-HTTP) subgraph execution.
