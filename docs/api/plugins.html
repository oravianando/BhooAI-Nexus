@bhooai/nexus-plugins Plugins API Manifest, host, hooks, trusted in-process + sandboxed worker plugins.

The plugin system. A plugin ships a plugin.json manifest declaring its name, capabilities, and lifecycle hooks, plus an entry module whose default export is a PluginModule with optional install / init / start / onConfigChange / stop functions. The PluginHost loads manifests from a directory, orders them topologically by dependencies, constructs a TrustedPlugin (in-process) or SandboxedPlugin (worker_thread) handle, and drives the lifecycle in order.

Manifest — capabilities & lifecycle

Capability

type Capability =
  | 'http'        // register routes / middleware
  | 'graphql'     // add (and host can remove) a subgraph
  | 'data'        // ODM models
  | 'auth'        // auth helpers
  | 'realtime'    // rooms / pubsub
  | 'scheduler'   // cron-style jobs
  | 'events'      // cross-plugin event bus
  | 'admin'       // admin pages / slots
  | 'fs'          // filesystem (allowlisted paths)
  | 'net';        // network (allowlisted hosts)

A capability grants access to a host registrar or resource. Sandbox mode gates every registrar by these; trusted mode checks them too (defense in depth — uniform contract with sandboxed plugins and lets the app audit usage). fs / net are only surfaced on PluginContext when granted.

const ALL_CAPABILITIES: Capability[] = [
  'http', 'graphql', 'data', 'auth', 'realtime', 'scheduler', 'events', 'admin', 'fs', 'net',
];

type LifecycleHook = 'install' | 'init' | 'start' | 'config:change' | 'stop';
const LIFECYCLE_HOOKS: LifecycleHook[] = ['install', 'init', 'start', 'config:change', 'stop'];

SandboxLimits

interface SandboxLimits {
  resourceLimits?: { maxOldGenerationSizeMb?; maxYoungGenerationSizeMb?; codeRangeSizeMb?; stackSizeMb? };
  heartbeatMs?: number;
  heartbeatTimeoutMs?: number;
  fsAllowPaths?: string[];
  netAllowHosts?: string[];
}

Per-plugin sandbox limits (sandboxed mode only). Passed to SandboxedPlugin via limitsByPlugin on PluginHost.load.

FieldTypeDefaultDescription
resourceLimits?object{ maxOldGenerationSizeMb: 64, maxYoungGenerationSizeMb: 16 }node:worker_threads resource limits. Sub-fields: maxOldGenerationSizeMb, maxYoungGenerationSizeMb, codeRangeSizeMb, stackSizeMb.
heartbeatMs?number—Heartbeat interval (ms) the worker reports while alive.
heartbeatTimeoutMs?number4000If a beat is missed within this window the worker is killed and the handle enters 'errored'.
fsAllowPaths?string[]—Filesystem paths the plugin may access (when 'fs' capability is granted). A path is allowed if it equals or starts with one of the entries; empty/absent = no extra restriction beyond the capability.
netAllowHosts?string[]—Hostnames the plugin may reach (when 'net' capability is granted). Matched against new URL(url).hostname; empty/absent = no extra restriction.

validateManifest(m)

function validateManifest(m: PluginManifest): void

Validate a manifest's shape. Returns void on success and throws on a missing/invalid field: name must match /^[a-z0-9-]+$/, version and entry are required, mode must be 'trusted' or 'sandboxed', every capability must be in ALL_CAPABILITIES, and every dependency must be a non-empty string.

import { validateManifest, ALL_CAPABILITIES } from '@bhooai/nexus-plugins';
validateManifest(manifest);   // throws on invalid; returns void otherwise
ALL_CAPABILITIES;             // ['http','graphql','data','auth','realtime','scheduler','events','admin','fs','net']

Hooks — HookBus & ServiceContainer

HookBus

class HookBus {
  publish(topic: string, payload: unknown): void;
  subscribe(topic: string, handler: (payload: unknown) => void): () => void;
  subscriberCount(topic: string): number;
}

A typed pub/sub bus for inter-plugin events. Subscribers are invoked synchronously per topic; publish iterates a snapshot of the set so a handler may unsubscribe during publish. subscribe returns an unsubscribe function. subscriberCount is for tests / inspection. This backs ctx.events on PluginContext.

const bus = new HookBus();
const off = bus.subscribe('user:created', (u) => console.log('new user', u));
bus.publish('user:created', { id: 42 });
bus.subscriberCount('user:created');  // 1
off();
bus.subscriberCount('user:created');  // 0

ServiceContainer

class ServiceContainer {
  register<T>(name: string, svc: T): void;
  get<T>(name: string): T;
  has(name: string): boolean;
  remove(name: string): void;
}

A minimal named-service container (inbuilt DI): register / get by name. register throws if the name is already taken; get throws if not found. This backs ctx.services on PluginContext.

const services = new ServiceContainer();
services.register('emailer', { send: async (m) => { /* ... */ } });
services.has('emailer');   // true
services.get('emailer');   // { send: ... }
services.remove('emailer');
services is gated by the events capability ctx.services.register / ctx.services.get require the events capability — there is no services capability. The capability policy maps both services.register and services.get to events, so a plugin that wants the DI container must request 'events' in its manifest.

The actual implementation the app provides for each registrar. The plugin context (trusted or sandboxed) delegates to these. Sandbox mode intercepts calls to enforce capability policy before reaching the bindings. ctx params are deliberately any (the host's RequestContext type lives in nexus-core; plugins should not import it directly — they receive a PluginRequest via the sandbox proxy).

  readonly pluginName: string;

  readonly config: unknown;
  readonly logger: { info(m: string, meta?: unknown): void; warn(m: string, meta?: unknown): void; error(m: string, meta?: unknown): void };
  http: {
    addRoute(method: string, path: string, handler: (ctx: any) => void | Promise<void>): void;
    addMiddleware(mw: (ctx: any, next: () => Promise<void>) => Promise<void>, phase?: 'before-route' | 'after-route'): void;
  };
  graphql: { addSubgraph(subgraph: { name: string; typeDefs: string; resolvers: unknown }): Promise<void> };
  data: { registerModel(name: string, schema: unknown): unknown; getModel(name: string): unknown };
  realtime: { join(room: string, connId: string): void; broadcast(room: string, msg: unknown): void };
  scheduler: { schedule(name: string, cron: string, fn: () => void | Promise<void>): void; cancel(name: string): void };
  events: { publish(topic: string, payload: unknown): void; subscribe(topic: string, handler: (payload: unknown) => void): () => void };
  admin: { registerAdminPage(page: AdminPageSpec): void; registerSlot(slot: SlotSpec): void };
  services: { register(name: string, svc: unknown): void; get(name: string): unknown };
  fs?: { readFile(path: string): Promise<Buffer | string>; writeFile(path: string, data: string | Buffer): Promise<void> };
  net?: { fetch(url: string, init?: { method?: string; headers?: Record<string, string>; body?: string }): Promise<{ status: number; body: string }> };
}

The facade a plugin's lifecycle functions receive. Every registrar is capability-gated (the trusted handle checks via requireCap in addition to any sandbox policy). fs and net are only present when the corresponding capability is granted; in sandboxed mode they're further restricted by SandboxLimits allowlists. There is no ctx.auth — 'auth' is only a capability value.

PluginModule

interface PluginModule {
  install?(ctx: PluginContext): Promise<void> | void;
  init?(ctx: PluginContext): Promise<void> | void;
  start?(ctx: PluginContext): Promise<void> | void;
  onConfigChange?(ctx: PluginContext, newConfig: unknown): Promise<void> | void;
  stop?(ctx: PluginContext): Promise<void> | void;
}

The plugin module shape: a default export factory returning lifecycle handlers. The host drives install → init → start in dependency order; stop runs in reverse. onConfigChange is invoked when a new config is pushed via PluginHandle.updateConfig (and in sandboxed mode also signals the 'config:change' hook to the worker).

// plugins/analytics/index.js
export default {
  async install(ctx) { ctx.log.info('analytics install'); },
  async init(ctx)  { ctx.log.info('analytics init'); },
  async start(ctx) {
    ctx.http.addRoute('GET', '/analytics/hit', (r) => r.json({ ok: true }));
    ctx.admin.registerAdminPage({ path: '/plugins/analytics', title: 'Analytics', group: 'Insights' });
    ctx.events.subscribe('user:created', () => ctx.logger.info('new user'));
  },
  async onConfigChange(ctx, newCfg) { ctx.log.info('config changed', newCfg); },
  async stop(ctx) { ctx.log.info('analytics stop'); },
};

PluginHandle

interface PluginHandle {
  manifest: PluginManifest;
  state: 'loaded' | 'installed' | 'initialized' | 'started' | 'stopped' | 'errored';
  install(): Promise<void>;
  init(): Promise<void>;
  start(): Promise<void>;
  stop(): Promise<void>;
  updateConfig(cfg: unknown): Promise<void>;   // re-validates + calls onConfigChange
  unload(): Promise<void>;                  // stop + (sandboxed) terminate the worker
}

A loaded plugin handle. Both TrustedPlugin and SandboxedPlugin implement this. updateConfig swaps the config on the context and (if the module implements onConfigChange) notifies the plugin; in sandboxed mode it signals the 'config:change' hook to the worker. unload stops the plugin and, for sandboxed plugins, terminates the worker thread.

Runtime — TrustedPlugin

class TrustedPlugin implements PluginHandle {
  readonly manifest: PluginManifest;
  state: PluginHandle['state'];   // 'loaded'
  constructor(manifest: PluginManifest, pluginDir: string, bindings: HostBindings, config: unknown);
  install(): Promise<void>;
  init(): Promise<void>;
  start(): Promise<void>;
  stop(): Promise<void>;
  updateConfig(cfg: unknown): Promise<void>;
  unload(): Promise<void>;
}

Trusted in-process plugin: the entry module is imported directly into the host (pathToFileURL + dynamic import()) and its lifecycle functions run with full Node API access. Every registrar on the context is checked against the manifest's capabilities (requireCap throws "lacks capability: <cap>" if missing) — defense in depth. A trusted plugin could reach the host directly, but going through the context keeps the contract uniform with sandboxed plugins and lets the app audit usage. fs/net are surfaced on the context only when the capability is granted; they're lazily imported from node:fs/promises / the global fetch.

const plugin = new TrustedPlugin(manifest, pluginDir, bindings, { region: 'us' });
await plugin.install();
await plugin.init();
await plugin.start();
await plugin.updateConfig({ region: 'eu' });   // calls module.onConfigChange if defined
await plugin.stop();
await plugin.unload();               // stop + clear module/ctx references

Sandbox — SandboxedPlugin & policy

SandboxedPlugin

class SandboxedPlugin implements PluginHandle {
  readonly manifest: PluginManifest;
  state: PluginHandle['state'];   // 'loaded'
  constructor(manifest: PluginManifest, pluginDir: string, bindings: HostBindings, config: unknown, limits: SandboxLimits = {});
  install(): Promise<void>;
  init(): Promise<void>;
  start(): Promise<void>;
  stop(): Promise<void>;
  updateConfig(cfg: unknown: Promise<void>;
  unload(): Promise<void>;
  getRestarts(): number;   // test helper: number of times the worker died
}

Sandboxed plugin: the entry runs inside a worker_thread with heap + event-loop isolation. A crash in the worker cannot take the host down. The host owns the real registrars (HostBindings); the worker calls them over a request/response RPC, and the host authorizes every call via authorize before forwarding. Route handlers registered by the worker run inside the worker — the host proxies inbound requests to the worker over invokeRoute and awaits the response. If the worker dies mid-request, the host returns 503 and rejects in-flight RPC / lifecycle waiters. A heartbeat watchdog (default 4000ms) terminates a worker that stops beating.

const plugin = new SandboxedPlugin(manifest, pluginDir, bindings, cfg, {
  resourceLimits: { maxOldGenerationSizeMb: 128 },
  heartbeatTimeoutMs: 5000,
  fsAllowPaths: ['/var/data/hello-worker'],
  netAllowHosts: ['api.example.com'],
});
await plugin.install();   // spawns worker, waits for 'ready', drives install via RPC
await plugin.start();
plugin.getRestarts();   // 0 unless the worker has died
await plugin.unload();   // stop + terminate the worker
v1 seams Sandboxed plugins run in a worker_threads sandbox with real heap/event-loop isolation (a crash can't take down the host) and capability-restricted RPC. They cannot add GraphQL subgraphs (resolvers aren't serializable — ctx.graphql is trusted-only) and sandboxed middleware is a no-op (the host logs a warning and does not apply it). The sandbox is not cryptographic — for truly untrusted plugins use child-process/OS isolation.

PolicyDecision

interface PolicyDecision {
  allowed: boolean;
  reason?: string;
}

Result of an authorization check. reason is present when allowed is false (e.g. "missing capability: events", "path outside allowlist: /etc", "host outside allowlist: evil.com").

authorize(method, args, capabilities, fsAllowPaths?, netAllowHosts?)

function authorize(
  method: string,
  args: Record<string, unknown>,
  capabilities: Set<Capability>,
  fsAllowPaths?: string[],
  netAllowHosts?: string[],
): PolicyDecision

Decide whether a sandboxed plugin may invoke an RPC method with the given args. The capability set is checked first against METHOD_CAPABILITY; for fs.readFile / fs.writeFile the path is additionally checked against fsAllowPaths (allowed if it equals or starts with an entry); for net.fetch the hostname (from new URL(url).hostname) is checked against netAllowHosts. Unknown methods (including logger, which is always allowed) are allowed by default.

RPC methodCapability
http.addRoute, http.addMiddlewarehttp
data.registerModel, data.getModeldata
realtime.join, realtime.broadcastrealtime
scheduler.schedule, scheduler.cancelscheduler
events.publish, events.subscribe, events.unsubscribeevents
admin.registerAdminPage, admin.registerSlotadmin
services.register, services.getevents
fs.readFile, fs.writeFilefs + path allowlist
net.fetchnet + host allowlist

Registry — PluginHost

class PluginHost {
  constructor(bindings: HostBindings, pluginsDir: string);
  load(configByPlugin: Record<string, unknown> = {}, limitsByPlugin: Record<string, unknown> = {}): Promise<string[]>;
  runLifecycle(hook: 'install' | 'init' | 'start' | 'stop'): Promise<void>;
  install(): Promise<void>;
  init(): Promise<void>;
  start(): Promise<void>;
  stop(): Promise<void>;
  updateConfig(name: string, config: unknown): Promise<void>;
  unload(name: string): Promise<void>;
  get(name: string): PluginHandle | undefined;
  list(): PluginHandle[];
  order(): string[];
}

Loads plugin manifests from a directory, constructs the right handle (trusted in-process vs sandboxed worker), orders them topologically by their declared dependencies, and drives the install → init → start → stop lifecycle in that order. stop runs in reverse dependency order and is best-effort (never throws). runLifecycle throws (and marks the handle 'errored') if a plugin fails install/init/start.

MethodDescription
constructor(bindings, pluginsDir)The pluginsDir is scanned for subdirectories containing a plugin.json.
load(configByPlugin?, limitsByPlugin?)Discover and load (but not start) all plugins. Reads each plugin.json, validateManifests it, topo-sorts by dependencies, and constructs a TrustedPlugin or SandboxedPlugin per mode. configByPlugin maps plugin name → its config object; limitsByPlugin maps plugin name → its SandboxLimits. Returns the load order (plugin names).
runLifecycle(hook)Run a lifecycle hook across all plugins in dependency order (reversed for 'stop').
install() / init() / start()Convenience: runLifecycle('install'|'init'|'start').
stop()Best-effort reverse-order shutdown; never throws.
updateConfig(name, config)Push a config change to one plugin (delegates to PluginHandle.updateConfig). Throws if name is unknown.
unload(name)Stop and remove a plugin (delegates to PluginHandle.unload); drops it from loadOrder.
get(name)The PluginHandle for name, or undefined.
list()All handles in load order.
order()The load order (plugin names).
 
import { PluginHost } from '@bhooai/nexus-plugins';

const host = new PluginHost(bindings, './plugins');
const order = await host.load(
  { analytics: { region: 'us' } },                       // configByPlugin
  { 'hello-worker': { heartbeatTimeoutMs: 5000 } },   // limitsByPlugin
);
await host.install();
await host.init();
await host.start();
host.order();          // ['analytics', 'hello-worker']
host.get('analytics'); // TrustedPlugin handle
host.list();           // [TrustedPlugin, SandboxedPlugin]
await host.updateConfig('analytics', { region: 'eu' });
await host.stop();     // reverse order, best-effort
await host.unload('analytics');

Admin — AdminExtensions

class AdminExtensions {
  registerPage(plugin: string, page: AdminPageSpec): void;
  registerSlot(plugin: string, slot: SlotSpec): void;
  removePlugin(plugin: string): void;
  listPages(): Array<AdminPageSpec & { plugin: string }>;
  groupedPages(): Record<string, Array<AdminPageSpec & { plugin: string }>>;
  listSlots(slot: string): Array<SlotSpec & { plugin: string }>;
  toJSON(): { pages: Array<AdminPageSpec & { plugin: string }>; slots: Record<string, Array<SlotSpec & { plugin: string }>> };
}

A registry the host fills as plugins register admin pages and slots. The admin app reads this (via the supervisor / control API or a direct endpoint) to render nav entries, pages, and dashboard widgets contributed by plugins. Pages are keyed by path and grouped by group (default 'Plugins'); slots are grouped by their slot name and ordered within it (default order = 100).

MethodDescription
registerPage(plugin, page)Add/replace a page keyed by page.path; stamps plugin onto the record.
registerSlot(plugin, slot)Append a slot entry; the array is (re)sorted by order (default 100).
removePlugin(plugin)Drop all pages and slots contributed by plugin (call on unload).
listPages()All pages sorted by order (default 100), each tagged with plugin.
groupedPages()Pages grouped by group (default 'Plugins'), preserving per-group order.
listSlots(slot)Slot entries for slot, ordered by order; [] if none.
toJSON()Snapshot { pages, slots } for serialization to the admin app.
 
const ext = new AdminExtensions();
ext.registerPage('analytics', { path: '/plugins/analytics', title: 'Analytics', group: 'Insights' });
ext.registerSlot('analytics', { slot: 'dashboard:top', component: './AnalyticsWidget', order: 10 });
ext.listPages();     // [{ path:'/plugins/analytics', title:'Analytics', group:'Insights', plugin:'analytics' }]
ext.groupedPages();   // { Insights: [ ... ] }
ext.listSlots('dashboard:top');  // [ { slot, component, order, plugin } ]
ext.toJSON();         // { pages: [...], slots: { 'dashboard:top': [...] } }
ext.removePlugin('analytics');

Two example plugins ship: plugins/analytics (trusted) and plugins/hello-worker (sandboxed).
